# PROJECT_STRUCTURE.md

A concise guide to the repository layout and responsibilities of the main folders and modules. Use this as a quick orientation when navigating the codebase.

## Top-level files & folders

- `pom.xml` — Maven build and dependency management.
- `mvnw`, `mvnw.cmd` — Maven wrapper (use to run mvn without installing Maven globally).
- `README.md` — Quick start and project summary.
- `PROJECT_STRUCTURE.md` — (this file) explains the layout and important modules.
- `WORKFLOW_DESIGN.md` — State machines, messaging flows, and DB schema overview.
- `docker/` — Docker assets and orchestration:
  - `docker-compose.yml` — Compose stack (app, Postgres, RabbitMQ, optional tooling).
  - `Dockerfile` — Multi-stage build for the Spring Boot app.
  - `postgres/`, `rabbitmq/` — container init scripts and config.
- `src/` — Application source and tests (detailed below).
- `docs/` — Documentation, Postman collection and test reports.
- `target/` — Build outputs and test reports (generated by Maven).

## `src/main/java/com/articurated/` — application code (by bounded context)

The code is organized to follow Domain-Driven Design (DDD) concepts. Each bounded context contains the usual layered structure (domain, application/service, infrastructure, presentation).

- `order/` — Order bounded context
  - domain: entities and value objects representing orders and line items
  - repository: JPA repositories for persistence
  - service / appservice: application orchestration (e.g., `OrderAppService`) and domain services
  - controller: REST API controllers for order CRUD and transitions
  - statemachine: `OrderStateMachineConfig` and transition actions

- `returns/` — Returns bounded context
  - domain: `Return` entity and related value objects
  - service / controller: handlers for create/approve/reject flows
  - statemachine: `ReturnStateMachineConfig` and transition actions (publish refund events)

- `messaging/` — Message producers and consumers
  - `MessageProducer` implementations that send messages to RabbitMQ
  - Consumers annotated with `@RabbitListener` to process invoice/refund messages

- `shared/` — Cross-cutting concerns
  - config: RabbitMQ, datasource, caching, and other configuration classes
  - events: `ApplicationEventHandler`, `EventMapper` extension point, domain-to-message mapping
  - exception: shared exceptions and error handlers
  - utils: common utility classes

## `src/main/resources/`

- `application.yml` — runtime configuration (profiles, datasource, RabbitMQ connection, ports). Update this for local dev or rely on Docker compose environment variables.
- `db/migration/` — Flyway SQL migrations (e.g., `V1__Create_orders_schema.sql`, `V2_1__Create_returns_schema_fixed.sql`). These define the canonical schema used by the app.

## Tests

- `src/test/java/` contains both unit and integration tests. Integration tests may rely on Docker services or Testcontainers. Test reports are generated under `target/surefire-reports` and `target/failsafe-reports`.

## `docs/`

- Postman collection(s), API test results, and additional documentation live here. See `docs/POSTMAN_COLLECTION_FULL.json` for example payloads and workflows used in end-to-end runs.

## Key modules & where to look

- State machines
  - `OrderStateMachineConfig` — order transitions and actions; check `order/statemachine`.
  - `ReturnStateMachineConfig` — return transitions and actions; check `returns/statemachine`.

- Event-to-message wiring
  - `EventMapper` (extension point) — implement new mappers to translate application events to outbound messages.
  - `ApplicationEventHandler` — discovers mappers and dispatches events (often using `@Async`).

- Messaging
  - `RabbitMQConfig` (under shared/config) — queue/exchange/binding definitions and bean configuration.
  - `MessageProducer` — publishing helper methods used by mappers and services.
  - Consumers in `messaging/consumer` — process invoice/refund messages.

- Persistence and history
  - `orders` and `returns` tables store current state in `current_state`.
  - `order_state_history` and `return_state_history` append a record for every successful state transition.

## How pieces fit together (quick flow)

1. Client calls `POST /api/orders` -> `OrderController` -> `OrderAppService#createOrder` -> persist order with `PENDING_PAYMENT`.
2. On `PUT /api/orders/{id}/transition?event=SHIP_ORDER` -> state machine transition executes `shipOrderAction` -> update DB state and append `order_state_history` row -> publish `GenerateInvoiceEvent` via `ApplicationEventPublisher`.
3. `ApplicationEventHandler` routes the event to a `GenerateInvoiceEventMapper` which calls `MessageProducer.sendInvoiceGenerationMessage(orderId)` -> RabbitMQ -> `InvoiceMessageConsumer`.

## Useful commands

PowerShell (Windows):

```powershell
.\mvnw.cmd clean package -DskipTests
.\mvnw.cmd test
cd docker; docker-compose up -d postgres rabbitmq
.\mvnw.cmd spring-boot:run
```

Unix/macOS:

```bash
./mvnw clean package -DskipTests
./mvnw test
cd docker && docker-compose up -d postgres rabbitmq
./mvnw spring-boot:run
```

## Maintenance tips

- Keep `application.yml` and `docker/docker-compose.yml` credentials/ports consistent; use `.env` for secrets referenced by compose.
- Add tests for each state-machine transition and one integration test that exercises the full order -> ship -> invoice generation flow.
- When changing transitions, update `*_state_history` migrations and add a migration that backfills missing metadata if needed.

## Mapping to the deliverables/spec

- The repository contains DDD scaffolding, state machines, messaging wiring, and Flyway migrations. Use `WORKFLOW_DESIGN.md` and `docs/POSTMAN_COLLECTION_FULL.json` for operational examples and E2E test scripts.
